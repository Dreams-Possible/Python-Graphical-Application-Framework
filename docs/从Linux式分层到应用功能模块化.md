# 从 Linux 式分层到应用功能模块化

## 1. 为什么需要记录这次转变

团队具有嵌入式开发背景，习惯从底层开始建立系统：先确定基础设施和接口，再逐层向上构建功能。这套方法在固件、驱动、操作系统组件和长期稳定的平台底座中非常有效。

当它被直接带入 Python + Qt 上位机开发后，项目最初也会呈现出结构整齐、职责明确的特点；但随着功能持续增加，一个需求往往需要同时修改多个全局层级，代码的局部可理解性下降，开发和维护逐渐困难。

这不是团队缺乏架构意识，也不是分层设计本身错误，而是设计对象发生了变化：

> 嵌入式系统通常在构建平台能力；上位机通常在既有平台上组合应用功能。

因此，架构的主要组织轴也需要从“技术层级”转向“用户功能”。

## 2. Linux 式系统设计思维

本文所说的“Linux 式”不是指 Linux 只有一种架构，而是概括团队熟悉的一类系统设计方法：从底层资源和稳定接口出发，逐层提供能力，严格控制依赖方向。

典型结构类似：

```text
应用与服务
    ↓
系统接口与公共子系统
    ↓
驱动与硬件抽象
    ↓
硬件资源
```

### 2.1 主要特点

- 从底层能力和稳定接口开始设计；
- 强调上下层职责、依赖方向和访问边界；
- 上层尽量不感知底层具体实现；
- 公共机制集中建设，再由多个上层功能复用；
- 重视硬件差异隔离、接口稳定性和长期兼容；
- 倾向先搭建完整骨架，再在骨架中填充功能。

### 2.2 优点

这种思维在以下方面非常强：

- **硬件适配清晰**：上层不需要理解寄存器、总线和具体驱动差异；
- **公共能力复用**：调度、通信、存储等底座可以服务多个上层模块；
- **依赖方向稳定**：底层不反向依赖具体业务，系统可以长期演进；
- **故障边界明确**：问题能够按硬件、驱动、服务和应用逐层定位；
- **适合多人建设平台**：不同团队可以围绕明确接口并行工作；
- **适合高稳定性接口**：底层接口一旦发布，可以长期支撑大量调用方。

### 2.3 代价

- 一个完整功能天然会跨越多个层次；
- 接口和抽象需要较高的前期设计成本；
- 局部变化可能需要评估大量上下游调用者；
- 为保持层级纯洁，容易产生只负责转发的中间层；
- 当系统规模不足时，平台化投入可能大于实际收益。

这些代价在操作系统、驱动平台和大型基础设施中通常值得承担，因为底层能力会被大量功能长期复用。

## 3. 应用层软件的现实

Python + Qt 上位机不是从裸硬件开始构建系统。它已经运行在多个成熟平台之上：

```text
Windows / Linux
    ↓
Python 运行时
    ↓
Qt 图形界面、事件循环、线程、定时器和 I/O 能力
    ↓
串口库、网络库、数据库、打包工具等成熟依赖
    ↓
上位机应用功能
```

大量传统意义上的“底层问题”已经由操作系统、Python、Qt 和第三方库解决。上位机团队的主要工作不再是重新建设通用运行平台，而是把设备能力、操作流程、数据和用户界面组合成可靠产品。

上位机需求通常以功能形式出现：

- 增加一种设备连接方式；
- 修改固件升级流程；
- 增加一个产测步骤；
- 调整日志查询和导出；
- 增加参数配置页面；
- 在某个流程中显示实时进度与最终结果。

因此，代码的主要组织方式应当尽量贴近需求的形状。

## 4. 将 Linux 式分层直接套入上位机的问题

### 4.1 一个功能被拆散到整个项目

全局分层通常形成这样的目录：

```text
ui/
viewmodels/
domain/
ports/
core/
```

一个固件升级功能可能同时出现在：

```text
ui/upgrade_view.py
viewmodels/upgrade_view_model.py
domain/upgrade_service.py
ports/jlink_adapter.py
core/events.py
main.py
```

每个文件单独看都符合层级规则，但理解和修改“固件升级”时，开发者必须在整个项目中来回跳转。结构的全局整齐，换来了功能的局部破碎。

### 4.2 简单需求被迫经过完整链路

一个按钮触发操作，可能被规定必须依次经过：

```text
View → ViewModel → Domain → Port → Core
```

如果还要求跨层通信统一经过全局消息总线，就会继续增加事件定义、订阅、取消订阅和状态同步。

当其中某些层只负责原样转发调用时，这些层没有真正隔离复杂度，只是增加了查找路径和维护成本。

### 4.3 Qt 被错误地视为可剥离插件

如果目标产品明确是 Qt 桌面应用，那么窗口、控件、事件循环、对象生命周期、Signal/Slot、线程归属和主线程更新规则本身就是应用运行方式。

为了让 ViewModel、任务管理或应用协调代码“完全不感知 Qt”，可能会重复实现：

- 一套独立于 Signal/Slot 的事件系统；
- 一套从 Python 线程回到 Qt 主线程的桥接机制；
- 一套脱离 Qt 对象生命周期的订阅管理；
- 一套额外的定时、调度和任务通知抽象。

这些抽象并没有让应用真正摆脱 Qt，因为最终界面仍必须回到 Qt 事件循环。它们只是形成了两套运行机制之间的转换成本。

### 4.4 抽象目标发生错位

嵌入式平台常常需要替换芯片、驱动或硬件实现，因此隔离具体底层具有直接价值。

Qt 上位机通常没有替换整个 UI 框架的现实计划。若为了理论上的可替换性设计大量接口，团队会长期支付抽象成本，却很可能永远得不到替换收益。

应隔离的是确实存在变化可能、复用价值或独立测试价值的内容，例如设备协议、升级算法和数据格式，而不是无差别地隔离整个 Qt。

### 4.5 架构检查取代了业务判断

严格分层容易把评审重点变成：

- 文件是否放在规定目录；
- 是否发生跨层 import；
- 是否通过统一 EventBus；
- 是否创建了指定接口和实现。

这些检查容易自动化，却不能直接证明功能易维护。真正重要的问题反而可能被忽略：

- 状态有几个所有者；
- 后台任务能否取消和安全退出；
- 修改一个功能需要理解多少无关代码；
- 用户看到的状态是否与设备真实状态一致；
- 错误能否被定位和恢复。

## 5. 应用功能模块化思维

应用层架构以用户能够识别的功能作为主要边界：

```text
src/
├── app/
├── features/
│   ├── device_connection/
│   ├── firmware_upgrade/
│   ├── production_test/
│   └── log_viewer/
└── shared/
```

它的核心不是取消分层，而是调整优先级：

> 项目级以功能模块化为主；模块内部根据真实复杂度按需分层。

### 5.1 主要特点

- 目录结构首先反映产品功能；
- 一个功能的大部分代码集中在同一模块附近；
- 简单功能保持简单，不预建完整层级；
- 功能复杂后，在模块内部拆分 View、ViewModel、Repository 或 Use Case；
- 模块之间通过少量公开入口协作；
- 公共能力在已经发生稳定复用后才提取；
- Qt 被视为既定平台，可以直接承担界面和应用运行时职责。

### 5.2 优点

- **需求与代码对应**：看到需求名称就容易找到代码位置；
- **修改范围局部化**：大多数需求可以限制在单个功能模块内；
- **认知成本更低**：理解一个功能时不必先掌握整个框架；
- **减少无意义转发**：简单调用可以使用明确的方法直接表达；
- **适合渐进演进**：复杂度出现后再增加抽象；
- **团队并行更自然**：不同开发者可以围绕不同功能模块工作；
- **便于功能级测试**：状态、行为和数据入口可以围绕功能组织测试。

### 5.3 风险和缺点

功能模块化也不是没有代价：

- 不加控制时，不同模块可能重复实现相似能力；
- 模块可能直接访问彼此内部，形成横向耦合；
- 大模块可能逐渐变成内部结构混乱的“功能巨石”；
- 公共能力提取过晚可能产生一定重复；
- 团队需要判断何时保持简单、何时拆分，而不能只照目录模板执行。

这些风险不能通过恢复全局重分层解决，而应通过模块公开接口、状态归属、依赖方向和演进条件管理。

## 6. 两种思维的对比

| 维度 | Linux 式系统分层 | 应用功能模块化 |
|---|---|---|
| 主要设计对象 | 平台、驱动、公共系统能力 | 用户功能和操作流程 |
| 主要组织轴 | 技术层级 | 功能模块 |
| 设计起点 | 底层能力与稳定接口 | 用户需求、状态与交互 |
| 依赖重点 | 严格控制上下层方向 | 控制模块边界和状态所有权 |
| 抽象时机 | 倾向提前定义公共接口 | 复杂度或复用出现后提取 |
| 一个功能的位置 | 分散在多个全局层级 | 集中在一个功能模块附近 |
| UI 框架定位 | 倾向隔离为可替换实现 | 承认为应用平台组成部分 |
| 通信方式 | 统一接口、总线或层间协议 | 直接调用优先，通知按需使用 Signal/Slot |
| 适合场景 | 操作系统、驱动平台、硬件抽象、公共基础设施 | 桌面应用、移动应用、业务工具和产品功能开发 |
| 主要风险 | 层级繁重、功能破碎、过度抽象 | 模块重复、边界松散、内部膨胀 |

两者不是先进与落后的关系，而是针对不同问题优化的工具。错误不在于使用分层，而在于没有根据当前设计对象调整主要组织方式。

## 7. 转变后的设计方式

### 7.1 从“先搭层”转向“先画功能边界”

旧思路：

```text
这个项目需要哪些层？
```

新思路：

```text
用户要完成哪些独立任务？
每个任务涉及哪些状态、操作和数据？
哪些内容必须由多个功能共享？
```

### 7.2 从“每层都有文件”转向“复杂度驱动拆分”

简单模块可以是：

```text
log_viewer/
├── view.py
└── log_source.py
```

当页面状态、数据来源或业务流程变复杂后，再演进为：

```text
log_viewer/
├── ui/
│   ├── view.py
│   └── view_model.py
├── data/
│   ├── repository.py
│   └── file_source.py
└── export_logs.py
```

架构不是项目创建时一次决定完毕，而是随着功能复杂度逐步生长。

### 7.3 从“Qt 无关”转向“Qt 边界明确”

新的目标不是让所有代码远离 Qt，而是明确哪些代码为什么依赖 Qt：

- View 和页面状态管理可以使用 Qt；
- UI 生命周期、Signal/Slot、定时器和线程切换统一使用 Qt；
- 纯算法、纯数据和协议解析不必依赖 Qt；
- 是否使用 Qt 由职责决定，而不是由全局禁令决定。

### 7.4 从“统一总线”转向“通信意图明确”

通信方式按语义选择：

- 明确的一对一命令：直接调用公开方法；
- Qt 对象状态通知：Signal/Slot；
- 一个模块向多个未知接收者广播：才考虑应用级消息机制；
- 后台结果回到 GUI 线程：使用 Qt 跨线程 Signal/Slot。

消息机制不是层级合规工具，而是具有明确使用条件的通信方式。

### 7.5 从“替换一切”转向“隔离真实变化”

不要为假设中的替换创建接口。优先隔离实际容易变化的部分：

- 不同设备型号；
- 不同通信协议；
- 不同数据存储方式；
- 外部工具和服务；
- 复杂且需要独立测试的业务流程。

Qt 本身只有在项目确实存在多 UI 框架目标时，才需要被抽象为可替换实现。

## 8. 仍然保留的系统设计经验

转向应用功能模块化不意味着放弃嵌入式开发积累。以下经验仍然重要：

- 接口表达清晰的责任和数据约束；
- 设备协议与业务显示逻辑分离；
- 资源的创建、使用和释放必须成对；
- 错误不能被静默吞掉；
- 并发和生命周期必须可控；
- 配置、日志和诊断信息必须可追踪；
- 公共能力应稳定、清晰并经过验证；
- 关键状态只能有一个可信所有者。

需要放弃的不是严谨，而是将严谨等同于固定层数、全局目录和无条件抽象。

## 9. 判断架构是否适合应用层

可以通过以下问题检查设计是否发生了真正转变：

1. 新增一个功能时，是否首先创建功能模块，而不是先向每个全局层级添加文件？
2. 修改某项功能时，主要改动是否集中在该模块附近？
3. 每个中间层是否真正承担决策、转换或隔离责任，而非原样转发？
4. Qt 是否在需要事件循环、线程、生命周期和 UI 状态的地方被自然使用？
5. 纯算法和协议代码是否仍能保持简单、独立测试？
6. 模块之间是否通过少量公开入口协作，而不是访问彼此内部？
7. `shared/` 中的能力是否已经被多个模块实际复用？
8. 是否能够解释每一个抽象正在解决的现实问题？

如果一个局部需求仍需穿越大量全局目录、事件定义和转发层，说明设计虽然改了名称，但主要思维尚未完成转变。

## 10. 最终原则

新架构的核心不是“不要分层”，而是：

> 以功能模块化组织应用，以状态和数据流保证一致性，在模块内部按复杂度进行必要分层，依靠 Qt 建立统一的应用运行机制。

Linux 式系统设计继续适用于平台、驱动和稳定公共基础设施；应用功能模块化用于组织用户直接感知的产品能力。二者可以共存，但必须由问题性质决定谁是主导，而不能把某一种结构当作所有软件的固定答案。
